# 티켓 본문 작성 가이드

티켓 본문은 **몇 달 뒤에 이 티켓을 처음 여는 사람**을 위해 쓴다. 그 사람에게는 지금 우리가
공유하는 맥락이 하나도 없다. 그래서 본문의 값어치는 분량이 아니라 **네 가지가 다 있느냐**로
정해진다: 왜 하는가 · 어디까지 하는가 · 무엇이 되면 끝인가 · 근거가 어디 있는가.

**대원칙 — 주제는 요청자의 원래 요청이다.** 상위 Epic 의 본문·코멘트, 조사에서 나온 다른
티켓은 배치와 참고의 근거일 뿐, 제목·작업 범위의 재료가 아니다. 요청의 고유어(기술명·
테이블명)가 제목과 배경에 남아 있어야 한다.

## 생성 최소 요건 — 무엇이 채워져야 티켓이 되나

티켓을 만들려면 아래 슬롯이 해소돼야 한다. 사용자의 첫 문장이 채운 것을 가려내고,
빈 슬롯은 **세 갈래로 나눠** 처리한다 — 전부 물어보면 인터뷰가 늘어지고, 전부 추론하면
방향이 틀린다(실측: 조사만 오래 하고 한 번에 낸 초안이 전혀 다른 일이 됐다).

| 슬롯 | 비어 있을 때 | 이유 |
|---|---|---|
| 주제·산출물 | **ASK** (무엇을 만들지부터) | 사용자만 안다 |
| 범위(1차 목표: 검토만/PoC/최소 구현) | **ASK** (choice, 조사 전에) | 사용자만 안다 — 방향을 가른다 |
| Epic 배치 | **ASK** (choice: 후보+없음+새 Epic 필요) | 후보는 코드가 주되 선택은 사용자 |
| 모듈(컴포넌트) | **INFER** (조사·제목 접두) — 갈리면 ASK | 대개 추론 가능 |
| 형태(구조) | **INFER** (규모 신호) — 갈림 크면 확인 | 판단 기준이 `04` 에 있다 |
| 마감 | ASK(date) — 위임이면 비워 둠 | 지어내면 안 되는 값 |
| 우선순위 | **INFER** (기본 P3-Minor) — 묻지 않는다 | 합리적 기본값이 있다 |
| 담당자 | **LATER** (Assigner 가 근거와 함께) — 묻지 않는다 | 다음 단계의 몫 |

ASK 슬롯은 **조사보다 먼저**(해석 확인 턴) 묻는다 — 사용자의 답이 조사를 간결하게 한다.
"알아서" 위임이 오면 ASK 슬롯도 INFER 로 강등된다(묻지 않고 기본값+근거 기록).

## 표준 구조

본문은 HTML 로 쓴다(에디터가 받는 형식). **섹션은 아래 네 개가 전부이고 순서대로 온다.**
Knowledge·References 같은 섹션을 따로 만들지 않는다(전부 '참고' 하나로 — 중복 섹션·영문
섹션명은 결함이다).

```html
<h3>배경</h3>
<p>왜 이 일이 필요한지 2~4문장. 계기가 된 사건·요청·장애를 티켓 키와 함께.</p>

<h3>작업 범위</h3>
<ul><li>포함: 이번에 하는 것</li><li>제외: 이번에 하지 않는 것(다음으로 미루는 것)</li></ul>

<h3>완료 조건 (DoD)</h3>
<ul data-type="taskList">
  <li data-checked="false">검증 가능한 조건 1</li>
  <li data-checked="false">검증 가능한 조건 2</li>
</ul>

<h3>참고</h3>
<ul><li>DL-123 "제목" — 이 티켓과 어떤 관계인지 한 마디</li>
    <li><a href="URL">문서 제목</a> — 무엇을 볼 수 있는지</li></ul>
```

## 섹션별 작성 방식

**배경** — "왜 지금 하는가"를 사실로 적는다. 계기가 된 사건·요청을 티켓 키와 함께
("컨슈머가 대량 실패했다(DL-9071)"), 감상("개선이 필요해 보인다")은 금지. 2~4문장.
**원 요청의 어휘를 유지한다** — 배경을 상위 Epic 의 문장으로 채우면 주제가 바뀐다.
조사에서 알아낸 결정·경위("캐시 TTL 15분 합의(DL-5018 코멘트)")는 여기나 참고에 키와 함께.

**작업 범위** — **하지 않는 것을 적는 게 절반**이다. 포함/제외를 나눠 적는다. 범위가 안
적힌 티켓은 리뷰 때마다 "이것도 포함인가요?"가 반복된다.

**완료 조건 (DoD)** — 각 항목이 독립적으로 **검증 가능**해야 한다. "설계한다"는 언제
끝인지 모른다 → "설계 문서 작성 및 리뷰 완료". 조건은 2~5개.

★ 검증 가능하다는 것은 **무엇을 보고 판정하는지가 항목 안에 있다**는 뜻이다. 판정 방법이
없으면 리뷰 자리에서 "됐나요?"를 다시 물어야 하고, 그 대답은 사람마다 다르다.

| 판정 방법이 없다 | 판정 방법이 있다 |
|---|---|
| 테스트 완료 | 실패하던 케이스(DL-9071 재현 경로)가 통과 |
| 통계가 잘 생성됨 | 대상 테이블에 Puffin NDV blob 생성 확인 |
| 성능 개선 | 2홉 100노드 조회 p95 < 2초 측정 결과 기록 |
| 연동 확인 | StarRocks 쿼리 플랜에 통계 사용이 표시되는 것 확인 |
| 문서화 | 실행·재생성 절차 README 작성 및 리뷰 완료 |

왼쪽 열은 "끝났다고 말하면 끝나는" 항목이다. 오른쪽 열은 **누가 봐도 같은 답이 나온다.**
★ DoD 가 5개를 넘고 서로 다른 단계(설계/구현/검증/연동)라면 그건 DoD 가 아니라
**Sub-Task 목록**이다 — 구조를 다시 판단하라(`04-work-breakdown.md`).

**참고** — 근거가 **이 일과 실제로 무슨 관계인지**를 한 마디로 붙인다. 모든 불릿에
실제 티켓 키 또는 `<a href>` 링크가 반드시 있어야 한다 — **링크 없는 문서 제목 나열은
검증 불가라 날조로 취급되어 삭제된다.** 관계를 못 적겠으면 그 티켓은 관련이 없는 것이다.
관련지식·참조정보(과거 결정, 비교 결론)도 별도 섹션이 아니라 여기 불릿으로.

## Epic / Task / Sub-Task 는 본문이 다르다

세 층은 답하는 질문이 다르다. 같은 글을 복사해 내리면 셋 다 쓸모가 없어진다.

| | Epic | Task/Story | Sub-Task |
|---|---|---|---|
| 답하는 질문 | 이 이니셔티브가 **왜 존재**하고 무엇이 되면 성공인가 | **왜** 이 일을 하고 전체가 어디까지인가 | **무엇을 어떻게** 끝내는가 |
| 배경 | 상세(비즈니스 계기·목표) | 2~4문장 + **Epic 배경은 반복하지 않고 키 참조 1문장** ("배경은 DL-101 참조, 이 Task 는 그중 ~를 맡는다") | 쓰지 않는다 — 부모에 있다 |
| 작업 범위 | 포함되는 Task 들의 지형(모듈·단계) | 전체 범위와 제외 항목 | 이 조각의 범위만 (1~3문장) |
| 완료 조건 | 이니셔티브 수준 결과·측정지표 (Task 단위 세부 금지) | 이 일 전체가 끝난 상태 | 이 조각이 끝난 상태(한 사람이 며칠 안에 판정 가능, 1~2개) |
| 참고 | 근거 문서·선행 Epic | 근거 티켓·문서 (자기 것) | 필요할 때만(부모를 보면 되므로 대개 생략) |

**상위 티켓과의 중복/독립 규칙**:
- **중복 금지** — 배경 서사를 아래로 복사하지 않는다. 부모의 배경이 필요하면 키 참조
  한 문장으로 대체한다. 부모·자식이 같은 참고 목록을 가지면 하나는 가짜다.
- **독립 필수** — 자기 산출물·자기 DoD·자기 참고는 자기 것이어야 한다. 부모 DoD 를
  나눠 가진 게 자식 DoD 다(합치면 부모 DoD 가 돼야 한다). 자식이 부모와 같은 DoD 를
  가지면 그 자식은 티켓이 아니라 복사본이다.

**Sub-Task 제목은 부모 제목을 베끼지 않는다.** "Avro 전환"(부모) 밑에 "Avro 전환 1",
"Avro 전환 2"를 두면 나중에 어느 게 어느 건지 모른다 → "topic-order-events Avro 전환".

## 하지 말 것

- **모듈이 같다는 이유로 관련 티켓을 붙이지 않는다.** 같은 주제여야 관련이다.
- **여러 티켓에 같은 참고 목록을 복사하지 않는다.** 항목마다 관계가 다르면 목록도 달라야 한다.
- **본문에 "후속 Sub-Task 후보" 를 글로만 적고 끝내지 않는다.** 정말 쪼갤 거면 `children`
  으로 실제 Sub-Task 를 만든다. 글로 적힌 후보는 티켓이 되지 않는다.
- **링크 없는 문서 제목을 나열하지 않는다.** ("아키텍처 결정 기록", "설계 노트" 같은
  제목만 덜렁 — 실측된 날조 패턴이다.)
- 없는 티켓 키·사람·날짜를 지어내지 않는다. 확인 못 한 것은 적지 않는다.

## 쪼갠 뒤 담당 배분

쪼개는 방식에 따라 배분 규칙이 다르다. 이걸 섞으면 배분이 무의미해진다.

| 쪼갠 방식 | 예 | 배분 |
|---|---|---|
| **기능 분화** — 하는 일의 성격이 다름 | 검증 스크립트 / 전환 실행 / 모니터링 | 그 일의 **모듈 소속자**에게. 모듈이 다르면 담당도 다르다 |
| **분량 분할** — 같은 일을 나눔 | 토픽 A·B·C 각각 전환 | **골고루** 나눈다. 한 사람에게 몰면 쪼갠 의미가 없다 |

분량 분할에서 한 사람이 두 건 넘게 가져가려면 이유가 있어야 한다(다른 사람이 그 대상에
접근 권한이 없다 등). 이유 없이 몰면 그건 배분이 아니라 그냥 목록이다.
