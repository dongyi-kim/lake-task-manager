# 업무를 티켓 트리로 쪼개는 법

"~~한 업무를 수행해야 한다"는 한 문장에서 **실행 가능한 티켓 트리**까지 가는 절차.
에이전트의 핵심 산출물이 이것이다.

## 절차

### 1. 먼저 찾는다 — 처음 하는 일인가

새 티켓을 만들기 전에 **반드시 과거를 뒤진다**. 실무에서 "새 업무"의 상당수는
이미 누군가 시작했거나, 논의만 하고 멈췄거나, 비슷한 걸 다른 이름으로 하고 있다.

- 검색은 **동의어·약어로 여러 번** 돌린다(CDC / 변경데이터캡처 / 실시간연동).
- 티켓만 보지 말고 **Confluence 문서**도 본다 — 설계 결정은 대개 티켓이 아니라 문서에 있다.
- 관련 티켓을 하나 찾으면 거기서 **링크를 타고 한 홉 더** 나간다.

찾은 결과에 따라 갈 길이 다르다:

| 상황 | 해야 할 일 |
|---|---|
| 진행 중인 티켓이 있다 | **새로 만들지 않는다.** 그 티켓을 갱신하거나 Sub-Task 를 붙인다 |
| 멈춘 티켓이 있다 | 왜 멈췄는지 코멘트를 읽고 **사용자에게 알린다**. 같은 벽에 다시 부딪힌다 |
| 담을 Epic 이 있다 | 그 Epic 밑에 만든다 |
| 아무것도 없다 | 새로 만든다. Epic 이 필요한 규모인지 판단한다 |

### 2. 되묻는다 — 정보가 모자라면 만들지 않는다

다음이 비어 있으면 **추측하지 말고 묻는다**(한 번에 2~3개씩, 최대 3~4턴):

- **범위** — 어디까지가 이번 일인가. 무엇은 안 하는가
- **완료 조건** — 무엇이 되면 끝인가
- **기한** — 언제까지인가. 상위 WBS Task 일정과 맞는가
- **모듈** — 어느 모듈 일인가(컴포넌트를 정해야 사람을 찾는다)

묻지 말아야 할 것도 있다. **찾아보면 아는 것은 묻지 않는다** — 관련 티켓, 이전 담당자, 모듈의
사람 목록은 도구로 확인할 수 있다. 사용자에게 되묻는 건 **사용자만 아는 것**에 한한다.

### 3. 쪼갠다

```
Epic          여러 스프린트에 걸치는 묶음. 이미 있으면 새로 만들지 않는다
 └ Story      가치가 도달하는 단위. SP 를 매길 수 있는 유일한 유형
 └ Task       가치 단위는 아니나 필요한 일(조사·설계·환경 구성)
    └ Sub-Task  한 사람이 며칠 안에 끝내는 실행 단위
```

**쪼개기 기준**

- 하나의 티켓은 **담당자 한 명**이 책임질 수 있어야 한다. 두 명이 필요하면 쪼갠다.
- Story 가 **SP 8 을 넘으면** 쪼갠다.
- **검증 가능**해야 한다. "설계한다"는 무엇이 나오면 끝인지 모른다 → "설계 문서 작성 및 리뷰 완료".
- 순서 의존이 있으면 **링크로 표현**한다(blocks / relates to). 제목에 "1단계"라고 쓰지 않는다.

**과잉 분해를 하지 않는다.** 아직 방식이 안 정해진 일을 5개 Sub-Task 로 쪼개면, 방식이 정해지는
순간 5개를 다시 만든다. **조사·설계 단계에서는 Task 하나**로 두고, 결과가 나온 뒤 실행을 쪼갠다.

#### 어떤 구조로 만들 것인가 — 네 갈래 판단 기준

"태스크를 만들자"는 한마디에 대해 실제로 고를 수 있는 구조는 넷이다. **기본값은 Task 하나**고,
거기서 올라가거나 쪼개는 데는 **근거가 필요하다**. 근거를 못 대면 올리지 않는다.

| 구조 | 언제 | 판정 신호 |
|---|---|---|
| **① Task 하나** (기본) | 산출물 하나, 한 사람이 며칠 안에 끝냄 | 완료 조건을 2~4줄로 다 적을 수 있다 |
| **② Task 하나 + Sub-Task N** | 산출물은 하나인데 **작업이 여러 사람/여러 대상**으로 나뉨 | "누가 어느 것을 맡을지" 나눠야 하고, 각 조각이 며칠짜리다 |
| **③ Task 여러 개** (같은 Epic 아래) | 산출물이 여럿이고 **완료 시점·검증 주체가 다름** | 모듈이 다르거나, 하나가 끝나도 다른 것은 안 끝난다 |
| **④ Epic 격상** | 여러 Task 의 합으로만 완료 판정이 되는 **별도 보고 단위** | 아래 네 조건을 **전부** 만족 |

**Epic 격상은 보수적으로 판단한다.** Epic 은 진척 대시보드·보고의 단위라 한번 만들면 계속
관리 대상이 된다. 어설프게 만든 Epic 은 영원히 60% 에서 멈춰 있는 유령이 된다.
다음을 **전부** 만족할 때만 새 Epic 을 만든다:

1. **기간** — 2 스프린트(약 4주) 이상에 걸친다
2. **규모** — 서로 다른 모듈·담당의 Task 가 3개 이상 필요하다
3. **자리 없음** — 담을 만한 **기존 Epic 을 먼저 찾아봤고**(`find_parent_epic`) 없다
4. **보고 단위** — 사용자가 이 묶음을 따로 진척 관리하려 한다

하나라도 확실하지 않으면 **격상하지 않는다.** 기존 Epic 아래 Task 로 두고, 왜 격상을 보류했는지
한 줄 남긴다("2주 규모라 Epic 격상 보류 — DL-101 아래 Task 로 둠"). 나중에 커지면 그때 올린다.

**흔한 오판 두 가지**

- *Sub-Task 로 충분한 것을 Task 여러 개로 만든다* — "설계/구현/검증"은 대개 한 산출물의
  단계지 별개 산출물이 아니다. 단계는 Sub-Task 다.
- *Task 로 충분한 것을 Epic 으로 만든다* — 일이 커 보인다는 느낌은 근거가 아니다.
  위 네 조건을 세어 보고, 못 채우면 Task 다.

#### 각 티켓을 어디에 둘 것인가 — Epic · 모듈 · 라벨

구조를 정했으면 각 티켓의 **자리**를 정한다. 세 값은 서로 다른 질문에 답한다.

**Epic — "이 산출물은 어느 이니셔티브에 기여하는가"**

- 후보는 `find_parent_epic` 이 준다. 새로 만들기 전에 **반드시 먼저 찾는다**.
- **항목마다 Epic 이 달라도 된다.** 여러 Task 를 만들 때 모듈이 다르면 붙을 Epic 도 다른 것이
  정상이다("[ETL] 실시간 처리 안정화"와 "[Observability] 대용량 적재 최적화"). 억지로 하나에
  몰면 남의 Epic 진척률이 오염된다.
- 마땅한 후보가 **여럿이거나 없으면** 사용자에게 묻는다(`kind=choice, field=epic`, 보기에
  "없음(최상위)" 포함). Epic Link 가 없는 티켓은 진척 대시보드에서 안 보이므로, 조용히
  아무 데나 붙이는 것이 가장 나쁘다.
- Epic 의 모듈과 Task 의 컴포넌트가 다르면 둘 중 하나가 틀린 것이다 — 확인하고 적는다.

**모듈(Component) — "이 일의 산출물을 누가 책임지는가"**

- `03-modules-and-people.md` 의 6모듈 정의로 **정확히 하나**를 고른다.
- 두 모듈에 걸치면 **컴포넌트를 둘 넣지 말고 Task 를 나눈다**(위 구조 판단 ③). 컴포넌트가
  둘이면 워크로드가 이중 계상되고, 어느 모듈 리더가 볼 일인지도 흐려진다.
- 담당자는 그 모듈 소속이어야 한다. 모듈과 담당의 소속이 어긋나면 배정이 틀렸거나
  컴포넌트가 틀렸다.

**라벨 — "나중에 이걸 어떻게 다시 찾을 것인가"**

- **기존 라벨을 먼저 본다**(`list_ticket_options(kind="labels")`). 같은 뜻의 라벨이 세 벌
  생기면 어느 것으로도 검색이 안 된다.
- 새 라벨을 붙일 수는 있지만, 기존 목록에 없으면 **승인 카드에 '신규 라벨'로 표시**된다 —
  사용자가 보고 판단한다. 오탈자·동의어를 새 라벨로 만들지 마라.
- `PMO_VIT` 는 경영진 보고 현안 전용이고 트리 최상위 하나뿐이다. **사용자가 말했을 때만** 붙인다.

### 4. 채운다

각 티켓에 대해:

- **summary** — 동사로 끝나고, 제목만으로 구분된다
- **description** — 왜 하는지(배경) + 완료 조건 + 관련 티켓/문서 키
- **component** — 모듈 하나
- **labels** — 기존 라벨을 먼저 확인. `PMO_VIT` 는 최상위 하나에만
- **assignee** — 근거 4종과 함께 제안(→ `03-modules-and-people.md`)
- **duedate** — 상위 WBS 일정을 넘지 않게

### 5. 검증하고 승인받는다

- `validate_ticket_plan` 으로 **먼저** 검사한다. 여기서 걸리는 걸 사용자에게 보이면
  사용자가 대신 디버깅하게 된다.
- 초안 전체(트리 + 담당자 근거 + 검증 결과)를 **한 화면에** 보여 주고 승인을 받는다.
- **승인 없이는 아무것도 만들지 않는다.**
- Task 를 먼저 만들고, 그 결과 키로 **두 번째 호출**에 Sub-Task 를 붙인다.

## 좋은 분해 / 나쁜 분해

**요청**: *"실시간 수집 파이프라인에 CDC 방식을 도입해야 한다"*

**나쁜 예** — 방식이 안 정해졌는데 실행을 쪼갬
```
Task  Debezium 설치
Task  Kafka 토픽 생성
Task  커넥터 설정
Task  모니터링 대시보드 추가
```
→ Debezium 으로 간다는 결정이 아직 없다. 다른 방식이면 넷 다 버린다.

**좋은 예**
```
Epic  DL-101 실시간 수집 체계  (기존 Epic 재사용)
 └ Task   CDC 도입 방식 검토 및 결정            [ETL]  ~2026-09-05
    └ Sub-Task  후보 3종 비교(Debezium/네이티브 CDC/폴링)
    └ Sub-Task  소스 DB 영향도 확인 (DBA 협의)
    └ Sub-Task  결정 문서 작성 및 리뷰
 └ Story  선정 방식으로 파이프라인 PoC 구축      [ETL]  (검토 완료 후 착수)
```
→ 결정이 나기 전엔 **검토만** 쪼갠다. PoC 는 자리만 잡아 두고 SP 는 나중에 매긴다.
