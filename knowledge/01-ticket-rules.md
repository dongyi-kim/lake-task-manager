# 티켓 작성 규칙

Lake 프로젝트(`DL`)에서 티켓을 만들 때 지켜야 하는 규칙. 에이전트가 초안을 짜기 전에 읽는다.

## 티켓 유형 고르기

| 유형 | 언제 |
|---|---|
| **Epic** | 여러 스프린트에 걸치는 **묶음**. 그 자체로는 실행하지 않는다. WBS Task 에 매달린다 |
| **Story** | 사용자/이용자에게 **가치가 도달**하는 단위. **Story Point 를 매기는 유일한 유형** |
| **Task** | 가치 단위는 아니지만 해야 하는 일(조사·설계·환경 구성·문서화) |
| **Bug** | 이미 동작하던 것이 깨진 것. 새 기능의 미완성은 Bug 가 아니라 Story/Task |
| **Improvement** | 동작은 하지만 느리거나 불편한 것 |
| **Sub-Task** | 담당자 한 명이 **며칠 안에** 끝내는 실행 단위. 부모가 이미 존재해야 만들 수 있다 |

새 업무를 받았을 때 **처음부터 Sub-Task 까지 쪼개지 않는다.** 무엇을 할지 합의되지 않은 상태에서
쪼개면 다시 만든다. Story/Task 를 먼저 세우고, 실행 계획이 잡힌 것만 Sub-Task 로 내린다.

## Story Point (중요한 운영 제약)

**SP 는 Story 유형에만 입력할 수 있다.** 현재 사내 Jira 화면 구성상 Task·Bug·Sub-Task·
Improvement 에는 Story Point 필드가 아예 없다. 그래서:

- 티켓을 **만들 때는 SP 를 넣지 않는다**(생성 API 에 SP 자리가 없다). Story 를 만든 뒤 따로 건다.
- 진척률을 SP 로 재려면 **그 Epic 아래 Story 가 있어야** 한다. Task 만 잔뜩 있는 Epic 은
  진척률이 건수 기준 근사치로만 나온다.
- SP 를 매기고 싶은 일이면 **Story 로 만드는 것이 맞다.** 유형 선택이 곧 측정 가능 여부다.

SP 척도는 피보나치(1·2·3·5·8·13). 8 을 넘으면 **쪼개라는 신호**다.

## 상위 연결 (Epic Link / parent)

- 최상위 Task 를 만들 때 **`epic` 을 반드시 명시**한다. 상위 Epic 밑에 넣으면 그 키를,
  일부러 Epic 없이 둘 거면 `null` 을 적는다. **생략은 거부된다** —
  빠뜨려서 생긴 고아 티켓과 일부러 최상위로 둔 티켓은 다르기 때문이다.
- **Epic Link 가 없는 티켓은 WBS 집계·진척률에서 통째로 빠진다.** 화면에 안 보인다는 뜻이다.
  Epic 없이 만드는 건 "집계에 잡히지 않아도 되는 일"일 때만이다.
- Sub-Task 의 `parent` 는 **이미 존재하는** 티켓이어야 한다. 그래서 Task 를 먼저 만들고
  두 번째 호출로 Sub-Task 를 붙인다(한 번에 섞어 보낼 수 없다).

## Component

Component = **모듈**이다. 워크로드·WBS 역인덱스가 이걸로 사람을 찾으므로 비워 두면 안 된다.
현재 모듈: `ETL` · `Catalog` · `Runtime` · `Workbench` · `Observability` · `DataOps` · `DevOps`.

**`사용자 VoC`** 는 특수 컴포넌트다. 사용자 요청에서 온 일임을 표시하며,
**진척률 계산에서 항상 제외**된다(계획된 일이 아니므로 분모를 흐린다).

## Label

- **`PMO_VIT`** — 경영진 보고 대상 현안. **트리에서 최상위 하나에만** 붙인다.
  상위가 이미 PMO_VIT 면 그 자손은 중복으로 걸러지므로, 자식에 또 붙이면 노이즈다.
- **`mock`** — 가상 데이터 표식. 실무 티켓에 절대 붙이지 않는다.
- 라벨은 자유롭게 만들 수 있지만, 없는 라벨을 **지어내기 전에** 기존 라벨 목록을 먼저 본다.
  같은 뜻의 라벨이 세 벌 생기면 어느 것으로도 검색이 안 된다.

## Summary (제목)

- **무엇을 하는지 동사로** 끝낸다. "CDC 검토" (X) → "실시간 수집 파이프라인 CDC 방식 도입 검토" (O)
- 모듈/대상이 제목에 있으면 검색에 걸린다. `[Workbench] 쿼리 튜닝` 같은 접두 표기가 관행이다.
- 제목만 보고 **다른 티켓과 구분**되어야 한다. "개선", "대응", "작업" 만 있는 제목은 나중에
  아무도 못 찾는다.

## Description

- **왜** 하는지(배경·계기)를 첫 문단에 쓴다. 몇 달 뒤에 이 티켓을 여는 사람은 맥락이 없다.
- 관련 티켓·문서는 **키와 링크로** 적는다. "이전에 논의된 건" 은 근거가 아니다.
- 완료 조건(Acceptance)을 적을 수 있으면 적는다. 없으면 언제 닫을지 아무도 모른다.

## 마감일 (duedate)

`YYYY-MM-DD`. 상위 WBS Task 의 종료일을 넘기지 않는다 — 넘기면 계획이 이미 깨진 것이므로,
날짜를 늘리기 전에 **상위 일정 조정이 필요한 상황임을 사람에게 알린다.**

## 한 번에 만들 수 있는 양

**최대 100건**(`MAX_ITEMS`). Jira 에는 **롤백이 없다** — 중간에 실패하면 앞의 것은 이미
만들어져 있다. 그래서 만들기 전에 전부 검증하고, 실패한 항목은 반드시 사용자에게 보고한다.
