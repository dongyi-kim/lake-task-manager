# 조회 기준과 재사용

조회 전에 필요한 대상·필드·근거를 정한다. 단건을 여러 번 읽기보다 여러 대상을 묶어 수집한다. 이미 얻은 근거는 로컬 조사 자료와 공유 캐시를 활용한다.

## 묶음 조회와 필요한 본문만 읽기

검색 전에 필요한 membership을 정한다. 기간 내 접수와 작업·완료를 구분하고 이전 접수 후 이월된 업무도 확인한다. 현재 `updated`의 종료일만으로 과거 활동을 제한하지 않는다. 광범위 metadata 검색은 첫 페이지에서 전체 snapshot을 준비할 수 있으므로 이유·규모·사용 계획을 정한다.

- 대상 key가 정해졌으면 `get_tickets(keys=[...])`로 100건 이하씩 묶어 읽고 후보 탐색은 `search_issues(detail="summary")`를 쓴다. 본문·논의가 필요하면 [선택 수집과 재사용](heavy-content.md)을 읽고 `include_description`·`include_comments` 중 필요한 것만 켠다. 두 옵션 기본값은 false다.
- `missingKeys`/`complete`는 티켓 반환, `descriptionMissingKeys`는 본문 누락, `commentsMissingKeys`·`commentsCoverage`는 댓글의 누락·완전성을 나타낸다. 미반환은 권한·비가시성 등의 미확인이며 존재하지 않거나 0개라는 증명이 아니다.
- 검색·`get_descendants`가 이미 반환한 상태·담당·부모 관계·본문은 재사용한다. 같은 값을 확인하려고 key마다 `get_ticket`을 반복하지 않는다. 빠진 필드, 꼭 필요한 최신 확인, 렌더링·편집 원문만 해당 key로 보완한다.
- 허용 응답량·서버 상한 안에서 묶고 실제 nextStartAt을 따른다. heavy 페이지는 최대 10티켓, 결과는 16MiB 한도다. 크기 오류 시 현재 그룹을 나누는 방법은 [선택 수집](heavy-content.md)을 따른다. 한도 내에서는 불필요하게 한 건씩 나누지 않는다.
- 댓글·이력·연관 문서는 실제 판단에 필요한 key만 읽는다. 이미 받은 완전한 댓글은 재사용하고, 전체 검토에 부족한 부분/미상 논의만 이어 읽는다. 전체 필요를 알면서 preview를 반복하지 않는다. 지원되지 않는 다건 이력 인자는 만들지 않는다.
- 중점 개발 진척은 Confluence 일간·주간·월간보고에도 있을 수 있다. 기간·모듈로 보고서 집합을 먼저 찾고 필요한 본문·revision을 읽어 여러 Task에 재사용한다. Jira 직접 링크가 없어도 기능·산출물·환경·담당·시점의 맥락으로 대응 근거를 남긴다. 한 문서가 여러 Task를 묶거나 한 Task가 여러 문서에 나뉠 수 있으며, 모호한 대응을 임의의 1:1 관계로 확정하지 않는다. Task마다 같은 문서를 검색·재조회하지 않는다.

업무 도구의 동시 실행 한도는 서버 전체 8개다. 독립 조회는 그 이내로 나누고, 다음 페이지 인자는 이전 응답을 받은 뒤 정한다. 용량 초과로 거절되면 실제 `retryAfterSeconds`를 따르고 동시 실행을 줄인다. 성공 응답은 재사용하며 현재 그룹의 거절·실패·미완료 호출을 먼저 끝낸 뒤 새 그룹을 시작한다. `executed=false`인 로컬 거절을 Jira 요청으로 세지 않는다.

MCP 단건 호출을 동시에 여러 개 보내도 Jira의 개별 요청 수가 줄어든다고 보장할 수 없다. 실제 Jira 검색 한 번으로 여러 본문을 받는 경로와 구분한다. 부하는 MCP 호출 수뿐 아니라 관측된 upstream 요청 수·응답량·시간으로 확인한다. 캐시로 끝난 읽기는 Jira 추가 요청이 없을 수 있으므로, 초회와 캐시 재사용의 효과를 구분한다. 관측값이 없으면 실제 API 부하가 줄었다고 단정하지 않는다. 근거 완전성을 희생해 호출 수를 줄이지 않는다.

## 시점과 재사용

- 실제 schema에 `cache_mode`가 있으면 필요한 원본 나이에 맞춰 `live`(원본 검증), `hot`(10분), `warm`(1일), `cool`(7일), `cold`(30일)를 선택한다. 생략은 기존 리소스별 정책이다. 현재 상태·게시 직전처럼 최신 검증이 필요하면 `live` 또는 실제 도구의 `fresh=true`를 쓴다. 사용자가 더 짧은 허용 나이를 지정하면 따르며, 실패를 피하려고 모드를 느슨하게 바꾸지 않는다.
- 긴 댓글·이력 또는 계층의 페이지 수집을 시작하기 전에 허용 원본 나이를 정한다. `live`의 각 호출은 같은 원본 페이지·계층을 다시 검증할 수 있다. 질문이 허용하면 처음부터 적절한 제한 나이로 읽고, 최신 검증이 필요한 경우에는 그 비용을 유지한다. 비용을 줄이려고 이어 읽는 도중 모드를 바꾸거나 옛 원본 시각을 새것으로 표시하지 않는다.
- 과거 보고도 최근 취소·수정이 실적 판단을 바꾸면 해당 근거를 갱신한다. 변경 불가능한 특정 문서 revision은 재사용할 수 있지만 최신 revision 확인과 구분한다.
- 검색 membership, 티켓 필드, 댓글, 문서 본문, 사진·Epic 이름의 나이는 다를 수 있다. 새 필드 하나를 읽었다고 전체 검색·조사의 기준 시각을 새것으로 표시하지 않는다.
- cache metadata가 없으면 수집 시각을 모른다고 표시한다. 로컬 저장 시각은 upstream 수집·검증 시각을 대신하지 않는다.
- snapshot의 다음 페이지는 같은 snapshot을 이어 읽는 것이다. 최신 검색이 필요하면 첫 페이지부터 다시 시작한다.
- 과거 기간이라는 이유만으로 `cool`·`cold`를 선택하지 않는다. 최근 정정·취소 여부가 결과를 바꾸는 검색 membership·문서 head는 필요한 나이로 검증하고, 이미 확인한 불변 revision 본문은 재사용한다. `cache.compliant`, `upstreamValidated`, `partial`과 원본 시각을 확인한다.
- 검색·다건 도구의 `strategy`는 실제 schema에 있을 때만 사용한다. `off`는 전체 조건 한 번의 검색, `people`은 검증 가능한 사람 조건 묶음, `full`은 논리 조건별 조회, `auto`는 기존 안전한 묶음 방식이다. 단계별 결과를 재사용할 근거가 없으면 `full`을 무조건 선택하지 않는다. `max_parts`(1~64, 기본64)는 서로 다른 실제 JQL의 상한이며 HTTP 페이지·재시도 수와 다르다. 알려진 초과 비용은 전체 검색으로 전환될 수 있고 실행 중 상한 오류는 완료 결과가 아니다.
- metadata 전용 검색의 snapshot은 30분 고정 결과다. 같은 JQL·snapshotId·cache_mode·strategy·max_parts로 이어 읽어도 새 검증이 아니다. 본문/댓글 포함 검색은 고정 snapshot 없이 두 포함 값과 같은 조회 조건으로 실제 nextStartAt을 따른다. 검증된 membership·필드 캐시는 공유하므로 새 조사라고 모두 지우지 않는다. `execution.physicalQueryCount`와 실제 REST 횟수는 다르다.

결과에 조사 기준 시각과 자료 수집 시각, 재사용·갱신 범위, 갱신하지 못한 이유를 필요한 만큼 명시한다. 실패 때 허용 나이를 조용히 늘리거나 오래된 자료를 최신 확인 완료로 표현하지 않는다.
