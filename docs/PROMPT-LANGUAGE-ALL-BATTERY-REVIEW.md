> 데이터: `JIRA_ENV=mock` (`jira820`)

## 1. 이 문서의 목적과 읽는 법

이 문서는 네 프롬프트 언어 배분의 전체 실험 결과를 **배터리별로 한 문서에서 바로 비교**하기
위한 것이다. 각 배터리에는 다음 두 가지를 함께 배치했다.

1. 실제 답변 중 네 방식의 차이가 드러나는 부분. 공통적인 제목·목록 형식은 `…`로 줄였다.
2. 실행시간·LLM 호출·토큰의 정량 비교와, 답변을 직접 읽고 내린 정성 평가 및 의견.

따옴표 안 문장은 `ab-*.json`, `log-*-compose.txt`, `log-*-create.txt`에 저장된 실제 출력에서
가져왔다. `…`만 편집자가 넣은 중략 표시이며, 인용 문구 자체는 의미를 바꾸지 않았다. S1은 2턴
시나리오이므로 정량값도 두 턴의 합계다. 시간은 실행 로그의 경과시간으로, 공급자 대기와 재시도가
섞였기 때문에 언어 자체의 속도라고 단정하지 않는다.

보존 범위는 배터리마다 다르다. 대화 배터리는 답변 전문이 남아 있다. Compose는 원 실행기가 각
HTML의 앞 260자만 로그에 저장했고, Create는 성공 본문 전문을 저장하지 않았다. 따라서 아래에는
**실제로 보존된 출력 전부와 구조·통과 여부·시간**을 사용하며, 저장되지 않은 본문을 재구성하거나
실제 답변처럼 꾸며 넣지 않는다.

실제 비교군은 다음과 같다.

| 실험군 | 실제 구현 |
|---|---|
| BASE | common/roles는 주로 영어, playbook·도구 설명·출력 계약은 한국어인 기존 혼합 |
| KO | common/roles/playbook과 도구 설명을 한국어로 사용; 식별자·파라미터는 영어 유지 |
| EN | common/roles/playbook은 영어지만 도구 설명은 한국어 유지 |
| GUIDE | system/role/playbook과 도구 설명은 영어, 사용자 입력·최종 출력은 한국어 |

따라서 현재 EN은 엄밀한 “전부 영어”라기보다 **영어 프롬프트 + 한국어 도구 설명**이고,
GUIDE가 사용자가 의도한 “내부 영어 + 한국어 입출력”과 더 가깝다.

## 3. S1 — 신규 기능 티켓 생성

### 사용자 대화

1. `우리 기존 etl 파이프라인에 iceberg puffin ndv 통계정보를 생성하는 기능을 추가구현하고 싶어`
2. `1차 목표는 PoC. 완료 조건은 Lake 내 Iceberg 배치적재 테이블에 통계 생성 Batch Job 구현. 단계별 Sub-Task 로. 알아서`

### 실제 답변 — 차이가 드러나는 부분

**BASE**

> 1턴: “추가 구현의 구체적인 목표와 배경, 완료 조건 등에 대한 정보가 필요합니다. 아래에서
> 선택해 주세요.”
>
> 2턴: “제목: `[ETL] Iceberg Puffin NDV 통계정보 생성 Batch Job 구현` … 하위 작업: 설계,
> 구현, 검증.”

정보가 부족한 첫 턴에는 초안을 만들지 않았고, 두 번째 턴에서 사용자가 준 PoC·Batch Job·단계별
Sub-Task를 부모 제목과 설계/구현/검증 3단계에 반영했다.

**KO**

> 1턴: “현재 관련된 티켓은 없지만, ETL 관련 업무가 활발히 진행되고 있습니다. 아래에서 선택해
> 주세요.”
>
> 2턴: “하위 작업 1: … Batch Job 구현 / 하위 작업 2: … Batch Job 검증.”

첫 턴은 안전하게 질문했지만, 두 번째 턴은 설계 단계를 빼고 구현·검증 2개로 줄였다. 카드의 부모
제목과 완료 조건도 설계 중심으로 좁아지는 부분이 있어 사용자의 전체 작업 범위와 완전히 맞지 않는다.

**EN**

> 1턴: “관련된 진행 중인 티켓이 여러 개 있으며, 구체적인 기록은 확인되지 않았습니다. 아래에서
> 선택해 주세요.”
>
> 2턴: “하위 작업: … 설계 / … 구현 / … 검증 … 현재 관련된 진행 중인 티켓으로 DL-5515와
> DL-5033이 있으며 … 과거 이력은 확인되지 않았습니다.”

구조는 BASE처럼 3단계를 지켰다. 다만 승인에 필요한 핵심보다 관련 티켓과 과거 이력 설명이 길어
가독성과 집중도가 떨어진다.

**GUIDE**

> 1턴: “티켓 초안은 다음과 같습니다. 아직 만들어지지 않았습니다 … 제목: `[ETL] Iceberg
> Puffin NDV 통계정보 생성 기능 설계` … 승인을 요청합니다.”
>
> 2턴: “제목: `[ETL] Iceberg Puffin NDV 통계정보 생성 기능 설계` … 포함: … 기능 설계 …
> 하위[0]: … 구현 / 하위[1]: … 검증.”

정보가 부족한 첫 턴부터 질문 없이 승인 가능한 초안을 만든 점이 가장 큰 안전성 실패다. 두 번째
턴에서도 부모 제목과 작업 범위를 “설계”로 한정해, 사용자가 명시한 Batch Job 구현 완료보다 좁다.

GUIDE는 BASE와 비슷한 시간 안에 답했지만 첫 턴에서 성급하게 생성했다. 이 시나리오는 정적
프롬프트 절감보다 **정보 부족 시 질문할지, 생성할지의 분기 안정성**이 훨씬 중요함을 보여 준다.

최초 하네스가 모든 군의 Sub-Task 수를 0으로 기록한 것은 `pending.children`을 누락한 계측
오류였으므로 이 평가에는 사용하지 않았다.

### 9.8 CMP9 — 짧은 본문 요청에서 만든 배경

- BASE: “데이터 처리의 효율성을 높이기 위해 … DL-9040 이니셔티브의 일환.”
- KO: “데이터 흐름의 효율성을 높이고, 사용자 경험을 개선하기 위해 요청.”
- EN: “데이터 흐름의 일관성을 확보 … 데이터 소비자와의 통합을 통해 발생한 요청.”
- GUIDE: “데이터 조회의 효율성을 높이고, 사용자 경험을 개선하기 위한 요청.”

모두 형식 계약은 통과했지만 서로 다른 일반적 동기를 채웠다. 사실 근거가 없는 동기 확장이라는
공통 약점이라 특정 언어군의 승리로 보지 않는다.

### 9.9 Compose 종합 의견

자동 점수는 모두 `8/9`지만 실패 위치와 실제 의미 품질은 다르다. KO는 CMP6의 명시적인 멘션
계약을 유일하게 수행했고 CMP1 상태 표현도 사람 기준으로 가장 정확했다. 반면 BASE·EN·GUIDE는
CMP1의 “완료/남음” 모순과 CMP6의 과잉 질문을 공유한다. GUIDE는 여기에 CMP5의 수치·상태
오귀속이 추가된다. **Compose만 보면 KO가 의미 품질에서 근소하게 우세하고 GUIDE가 가장
위험하다.** 다만 네 방식 모두 CMP2·CMP9에서 일반적 동기를 만들어내므로 절대 품질은 충분하지
않다.

부모 없는 Sub-Task를 만들고, PASTE1에서는 충분한 원문이 있는데도 질문으로 돌렸다. EN은 ASK1,
BUG3, RULE1에서 질문과 초안을 함께 내는 경향이 가장 강했다. KO는 RULE1은 가장 안전했지만
ONE1의 출처 없는 참고, PAR1 본문 누락, STARR1 과잉 격상과 긴 실행시간이 약점이다.

**Create 사람 판정은 BASE > KO ≈ GUIDE > EN**이다. 다만 BASE도 ASK1·DUP1·BUG1에서
안전성 계약을 어겼으므로 우수하다는 뜻이 아니라 네 후보 중 상대적으로 덜 위험하다는 뜻이다.

## 11. 전체 배터리별 최종 판정

### 11.1 대화 배터리

| 배터리 | 정량 우위 | 정성 우위 | 핵심 판정 |
|---|---|---|---|
| S1 신규 생성 | 토큰 EN, 시간 BASE | **BASE** | GUIDE의 성급한 생성과 범위 축소가 위험 |
| S2 Bug 초안 | **BASE** | **BASE ≈ GUIDE** | EN의 상태 모순, GUIDE의 추가 비용 |
| S3 이력 | **GUIDE** | **EN ≈ KO** | GUIDE의 근거 초과 해석, BASE의 인용 매핑 오류 |
| S4 사람 업무 | **EN** | **KO ≈ EN** | 네 방식 모두 담당/수정/완료 구분 또는 완결성 미달 |
| S5 우선순위 | **BASE** | **BASE** | BASE만 D+1/D+9를 정확히 구분 |
| S6 진척 | **GUIDE** | **BASE** | GUIDE는 가장 빠르지만 근거 없는 인과 생성 |

### 11.2 계약 배터리

| 배터리군 | 자동 결과 | 사람 판정 | 핵심 차이 |
|---|---|---|---|
| Compose 9건 | 모두 8/9 | **KO > BASE ≈ EN > GUIDE** | KO만 멘션 수행; GUIDE 수치·상태 오귀속 |
| Create 23건 | BASE/GUIDE 18, KO/EN 16 | **BASE > KO ≈ GUIDE > EN** | 질문+초안, 중복, 부모 없는 Sub-Task에서 자동 점수 왜곡 |

정량 승자와 정성 승자는 자주 일치하지 않았다. 대화 S3·S6은 GUIDE가 가장 빠르고 토큰도 적지만
의미 정확도에서는 지지 않았다. Compose는 자동 점수가 모두 같지만 KO만 핵심 멘션 계약을
수행했다. Create는 BASE와 GUIDE의 자동 점수가 같지만 GUIDE의 RULE1은 실제 규칙 위반이다.
따라서 총 토큰·평균 지연·자동 통과율만 최적화하면 잘못된 결론에 도달한다.

## 12. 최종 의견

전체 대화·Compose·Create를 함께 보면 **BASE를 프로덕션 기준선으로 유지**하는 것이 맞다.

- BASE는 S1의 안전한 질문, S5의 정확한 날짜 계산, S6의 근거 분리처럼 실무 피해가 큰 지점에서
  가장 안정적이며 Create에서도 상대적으로 덜 위험했다.
- KO는 Compose의 상태·멘션과 RULE1 질문 행동이 가장 좋았지만, 전체 대화 토큰 27.6% 증가,
  STR1 462초, 본문 누락과 과잉 Epic 판단 때문에 전면 전환 근거가 부족하다.
- EN은 대화 총 토큰이 5.5% 적고 검색 커버리지가 좋지만, 상태·기한 오류와 Create의 공격적인
  무근거 초안 생성 때문에 BASE를 대체하기 어렵다.
- GUIDE는 Create 비용과 일부 시나리오 시간이 가장 낮지만, 성급한 생성, 근거의 주어·날짜·상태
  오귀속, 부모 없는 Sub-Task 생성 때문에 안전성이 가장 낮다.

이 결과를 “영어보다 혼합 언어가 본질적으로 낫다”로 일반화해서는 안 된다. 실제 차이를 만든 것은
언어 자체보다 질문/생성 분기, 도구 재호출, 날짜 계산, 근거 귀속, 체커 강도였다. 다음 비교에서는
EN과 GUIDE의 정의를 명확히 분리하고, 실행 순서를 무작위화해 최소 5회 반복하며, 모든 원 응답을
전문 저장해야 한다. 그 조건에서도 GUIDE가 사실성과 안전성을 유지하면서 비용 우위를 보일 때만
내부 영어화를 채택하는 것이 타당하다.
