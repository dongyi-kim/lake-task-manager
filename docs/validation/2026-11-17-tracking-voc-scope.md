# Tracking 사용자 VOC 수집 범위 검증

## 보고된 조건

- 담당자: ETL 모듈 구성원
- 컴포넌트: `사용자 VoC`만 존재
- 보고자: 별도 보고용 봇
- Task 창에는 보이지만 Tracking에서는 누락. 조회 건수 제한 여부 확인 요청.

## 확인한 차이와 수정

- Task의 모듈 조건은 구성원 담당자 **OR** 구성원 보고자 **OR** 모듈 컴포넌트.
- Tracking의 구성원 조건은 VOC 담당자에만 적용됐고, 다른 모듈 컴포넌트·Epic 연결이 있으면 제외했음. 티켓 종류·VOC 이름에 의존하는 제한과 다른 모듈의 배제 조건 제거. 자기 담당자·보고자 일치를 부모 조회보다 먼저 판단.
- 가벼운 후보 조회에 `reporter` 필드 추가. 별도 사용자 조회 없음. 불완전한 사용자 식별자는 확정적으로 제외하지 않고 원본 조회로 확인.
- Tracking은 설정된 검색 프로젝트로 후보를 제한했지만 Task의 모듈 담당자·보고자 조회는 프로젝트 제한이 없음. 설정된 프로젝트 범위에 선택 모듈 담당자·보고자 조건을 OR로 추가. 기간 조건과 명시적 사람 선택의 이력 기준 유지.
- 모듈명은 Jira 컴포넌트명과 항상 같지 않으므로 전역 컴포넌트 JQL은 추가하지 않음. 컴포넌트·Epic·부모를 통한 수집은 기존 설정 프로젝트 범위를 유지.
- 이전 버전의 중단된 조회는 후보 검색 체크포인트만 한 번 갱신. 이미 수집한 원본·이력·댓글은 재사용. 완료된 저장 결과는 스냅샷이므로 새 `조회`가 필요.

## 검증 근거

- Tracking 백엔드·프런트엔드 및 Task 모듈 조회 관련 테스트 385건 통과. 최종 후보 JQL 수정 후 Tracking 백엔드 전체 221건 재검증 통과. 독립 코드 리뷰의 전역 컴포넌트 JQL 우려를 반영한 뒤 차단 지적 없음.
- Task의 실제 `_matches_scope`와 Tracking의 모듈 판정을 비교. VOC·일반 티켓, 담당자·보고자·컴포넌트, 타 모듈 연결, 미확인 부모·사용자 식별자 검증.
- 요청 필드만 반환하는 공급자로 후보 조회부터 최종 저장 결과까지 검증. 해당 VOC 한 건은 기존 4회 REST 호출, 캐시 재사용 시 후보 재검증 1회. 별도 사용자 호출 없음.
- 실제 JQL 구문 트리를 평가해 설정 프로젝트 밖의 담당·보고 VOC 포함, 무관한 티켓·기간 이전 변경 제외, 따옴표·역슬래시 이스케이프 검증.
- 중단된 구버전 조회 재개 시 기존 두 티켓 원본을 다시 읽지 않고 신규 VOC 두 건을 추가 수집.
- 일반 티켓 170건 뒤에 VOC 120건을 배치. 서버 페이지 크기 50·100 모두 후보 290건을 끝까지 읽고 VOC 120건·이벤트 360건 보존. 원본 조회도 100+20건으로 진행. 캐시 재사용 결과 동일.
- 위 페이지 검증은 수정 전 main 코드에서도 통과. `maxResults=100`은 페이지 크기이며 전체 수집 제한이 아님.
- 개발 mock 서버에서 2026-11-10~17 ETL 새 조회 완료: 후보 418건, 분석 대상 163건, 맥락 포함 티켓 184건 중 VOC 53건. 수집 누락 표시 없음.

## 운영 확인 범위

알려진 필터 차이는 수정했지만 운영에서 VOC 전체가 누락된 정확한 원인은 아직 확정하지 않음. 보고된 단순 조합은 수정 전에도 기본 VOC 이름·일치하는 담당자·프로젝트 조건에서는 포함됨. 실제 누락 티켓 번호와 조회 기간으로 프로젝트, 사용 중인 버전, 저장 결과 재열람 여부를 대조해야 함.
