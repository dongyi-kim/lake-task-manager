# 대형 본문·댓글 수집 검증

## 변경

- Tracking 검색·댓글 페이지는 진행 위치와 건수만 저장. 원문은 합쳐진 목록 한 곳에 유지해 같은 페이지의 본문 중복 직렬화 제거.
- 이전 형식의 체크포인트·캐시도 원문과 진행 위치를 대조한 뒤 전환. 불일치 상태는 완료 처리하지 않음. 다른 수집이 채운 전체 댓글 캐시로 대체할 때는 이전 부분 페이지의 진행 정보를 제거.
- 응답 바이트 집계는 긴 문자열을 작은 조각으로 계산. 전체 응답 또는 단일 거대 문자열의 임시 복사본 생성 방지. UTF-8·이스케이프·JSON 타입을 포함한 기존 측정값 보존.
- MCP evidence의 8KiB 반환 예산 검사는 거대한 후보를 먼저 제외. 원문 SHA-256 계산도 작은 UTF-8 조각으로 처리. 기존 분할 반환·cursor·해시·원문 재조립 계약 유지.
- MCP `get_ticket`의 `summary`는 본문 렌더링 생략. `read`·`edit`는 요청한 본문 형태만 조립. 기본 `full`과 UI 동작·원본 캐시·Jira 호출 방식 유지.

## 메모리 재현

원문은 측정 전에 생성. 수치는 `tracemalloc`의 해당 연산 추가 Python 메모리이며 전체 앱 RSS가 아님.

| 연산 | 기존 | 수정 |
|---|---:|---:|
| 약 6MB 페이지의 정확한 바이트 집계 | 약 10.5MB | 1MB 미만 |
| 14,680,075바이트 단일 Unicode 본문의 정확한 집계 | 약 33.6MB | 약 133KB |
| 약 14MB evidence 페이지의 예산 초과 검사 | 33,555,784바이트 | 520바이트 |

마지막 행의 반환값 `8193`은 실제 원문 길이가 아니라 **8KiB 초과** 표시. 원문·분할 내용은 변경하지 않음.

## 데이터 보존 검증

- 실제 Playwright native request context: 2MiB 응답 8회, JSON·텍스트·첨부·오류 경로에서 처리 후 응답 본문 해제와 같은 context의 다음 호출 확인.
- Tracking source: 약 1.7MiB 댓글과 약 0.5MiB 렌더링 본문, 검색 본문. 단일 보관, 기존/신규 체크포인트 재개, 페이지 clamp, 전체 캐시 대체 검증.
- Tracking manager: 1,300,035바이트 댓글 두 개. 한 달 조회에서 두 번째 페이지에 `UpstreamBusy` 주입 → SQLite 체크포인트 → 새 manager → 이어 수집 → 화면 조회 → 캐시 재조회. 원문·HTML 길이와 SHA-256 일치. 호출 offset `[0, 1, 1]`로 완료 페이지 재조회 없음.
- MCP description: 약 1.17MB 원문. 읽기·편집 본문 끝까지 보존하고 사용하지 않는 변환 생략. 기본 UI 결과 유지.
- MCP evidence: 한글·emoji·이스케이프를 포함한 큰 댓글의 모든 조각 재조립, byte budget·cursor·SHA-256 일치.

Jira REST 호출 수를 줄이기 위한 기존 페이지 크기와 캐시는 유지. 검증은 로컬 fixture·로컬 HTTP 서버로 수행하며 운영 Jira를 부하 테스트하지 않음. 테스트 임시 데이터는 OS 임시 디렉터리에서 실행 후 정리.

최종 관련 회귀 검증: **474 passed / 141.23초**, skip 없음. Tracking 전체, 대형 응답·SSO 해제, MCP 본문·evidence·프로파일·인증·stdio·workspace, 티켓 뷰, Jira 스케줄러, MCP 용량 검증 포함. 전체 저장소 suite 결과를 의미하지 않음.

## 남은 경계

SSO transport는 개별 upstream 응답을 여전히 메모리에서 수신·해석한다. 저장 결과에도 화면·분석에 필요한 원문이 존재한다. 이번 변경은 불필요한 복사·중복 저장·사용하지 않는 렌더링을 줄인 것이며, 임의 크기의 전체 조회에 대한 고정 RAM 상한을 구현한 것은 아님. 큰 단일 evidence 기록의 분할 요청마다 전체 JSON과 해시를 다시 계산하는 CPU 비용도 남음.
