# App·MCP·API 과부하 보호

목표: 지연보다 앱 생존 우선. 새 작업은 처리 여유가 있을 때만 시작. 중단된 수집은 미완료 페이지부터 재개. 이미 실행된 쓰기는 자동 재전송하지 않음.

## 수용량과 제어 경로

| 경로 | 동시 수용량 | 초과 시 동작 |
|---|---:|---|
| 일반 HTTP API | 8 | 처리 전 429, `executed:false`, `Retry-After:1` |
| 첨부 업로드 | 1, 일반 API 수용량에도 포함 | 처리 전 429 |
| Tracking 취소 | 별도 2 | 추가 취소 요청만 429 |
| MCP HTTP 파싱·응답 | 16 | SDK 실행 전 429 |
| MCP 업무 / 인증·상태 도구 | 기존 8 / 별도 2 | 업무 초과 요청은 실행 전 거절 |
| Tracking 수집 | 1 | 추가 수집·재개 거절, 새 체크포인트·스레드 생성 없음 |
| SWR·쓰기 후 재조회 | 실행·대기 합계 8, 실행 1 | 기존 캐시 유지, 이후 조회에서 재시도 |

`/api/health/live`, 앱 열기·종료는 일반 요청 및 취소 작업과 분리. 실행 중인 동기 작업은 HTTP 호출자가 연결을 끊어도 완료 전 수용량을 반환하지 않음. 본문 수신 중 단절은 핸들러 실행 전에 종료. 업로드의 동기 Jira 호출은 이벤트 루프 밖에서 실행.

HTTP JSON 최대 16MiB, 첨부 전송 최대 65MiB(파일 64MiB와 multipart 여유). 요청 본문은 256KiB 이후 OS 임시 파일에 보관, 64KiB 단위로 파서에 전달. 본문 수신 제한 30초. 초과·시간 초과·취소·실패 시 임시 파일 정리. 기존 Confluence 첨부 10MiB 제한 유지.

## 메모리 압박

- 프로세스 메모리와 OS 가용 메모리 카운터를 최대 0.5초마다 확인. 상태 확인 API는 마지막 결과만 읽음.
- 프로세스 소프트 제한: 물리 메모리의 1/4, 최소 256MiB·최대 1GiB. OS 여유분: 물리 메모리의 1/20, 최소 128MiB·최대 512MiB.
- 한도 도달 시 새 API·MCP 업무·Tracking 실행·백그라운드 갱신 거절. Tracking은 다음 페이지 시작 전 중단하고 기존 체크포인트 보존.
- 사용량이 소프트 제한의 85% 미만, OS 여유가 예약량의 125% 초과일 때 재허용. 경계에서 수용·거절 반복 방지.
- 운영 Windows 작업 프로세스와 자식 Chromium은 하나의 Job에 포함. 메모리 commit 상한은 물리 메모리의 1/3, 최소 512MiB·최대 2GiB. 복구 관리자 프로세스는 Job 밖에 유지.

## 본문 포함 다건 검색

`include_description=true`는 전체 검색 결과를 모으는 정규화 스냅샷 경로에 진입하지 않음. Jira 검색 페이지별로 수집하며 개별 티켓 GET으로 전환하지 않음. 일반 메타데이터 검색의 기존 스냅샷·캐시 공유 유지.

- 물리 페이지 최대 10건, MCP 검색 페이지·다건 결과 최대 16MiB. 초과하면 오류와 작은 `max_results`·키 묶음 사용 안내. 본문 일부를 버린 성공 응답 없음.
- `nextStartAt`은 실제 반환 건수로 계산. 메타데이터 검색의 100건 페이지와 분리. 내부 full-ticket prefetch도 모든 페이지를 따라가며 단건 GET으로 되돌아가지 않음.
- 본문 검색은 `snapshotId:null`, `snapshotFrozen:false`. 과거 본문 스냅샷 커서는 첫 페이지 재시작 안내. 조회 도중 원본이 변경되면 페이지 사이 결과가 달라질 수 있으므로 전체 시점 고정 결과로 해석하지 않음.
- 같은 앱·인증 세션의 본문 페이지 캐시 재사용. 재기동·provider 교체·SSO 갱신은 다른 캐시 구획 사용. `currentUser()`·상대 날짜의 해석 결과 포함. 계정 전환 중 응답은 반환하지 않음. 캐시의 원래 수집 시각·읽기 등급 유지.
- 내부 정규화 본문 검색은 누적 32MiB 초과 시 전체 집계·스냅샷 게시 중단. 본문용 정규화 캐시 이름을 변경해 이전 무제한 집계 캐시와 분리.

1만 건 후보에서 본문 1건을 요청한 경우 Jira 검색 1회·반환 1건, 전체 스냅샷 생성 없음 확인. 3건 소규모 다건 본문은 첫 조회 Jira 1회·같은 조회 재실행 0회. 2MiB 본문 11건은 큰 페이지 거절 후 5·5·1건으로 모두 수집하고 각 본문의 SHA-256 일치 확인.

## 반복 장애 복구

운영 실행은 반복 장애 후 종료하는 대신 30→60→120→240→300초 간격으로 재시도. 앱 프로세스와 독립된 복구 트레이에서 즉시 재시도·종료 가능. 정상 종료 또는 사용자 종료는 재기동하지 않음. 업데이트 프로그램의 정상 종료 후 분리 동작 유지.

실행 중인 앱 식별은 가벼운 상태 확인 경로 우선. 유효한 앱 식별 정보가 있는 503 복구 응답도 기존 인스턴스로 인식. 일반 API가 밀렸다는 이유로 중복 앱을 실행하지 않음.

## 검증 범위

- 15명·10 Epic·30 Task·60 Subtask, 한 달의 생성·완료·댓글 300건.
- API 작업 8개와 MCP 작업 8개를 유지한 상태에서 Tracking 수집. 추가 API 100개·MCP 10개·Tracking 생성 25개 거절, 저장된 수집 건수 및 체크포인트 불변, liveness 응답 확인.
- API 본문과 댓글 각각 2MiB의 SHA-256 보존. 재개 후 100개 티켓·300개 이벤트 복구, 이미 완료한 댓글 페이지 재조회 없음.
- HTTP 취소 중 동기 작업·파일 쓰기 수명, 스트리밍 응답 정리, MCP 제어 도구 여유, 압박 시 쓰기 미실행·동일 mutation ID 재시도 검사.
- AI 요약 게시와 수집 재개가 겹쳐도 요약 저장이 수집 체크포인트를 이전 값으로 되돌리지 않음. 요약 저장은 snapshot 열만 원자적으로 갱신.
- Windows 실제 Job 상한 64MiB를 확인한 뒤 폐기 가능한 자식에서 128MiB 할당 시도. 시스템 메모리를 소진하지 않고 `MemoryError`·후속 자식 정상 실행 확인.
- 실제 Windows 복구 트레이 메시지 루프·Retry/Quit 콜백·숨김·종료 확인.

최종 통합 검증: **1,021 passed / 314.20초**, 실패·skip 없음. Tracking 전체, Jira query 전체, API routes 전체, 관련 런타임·MCP·world·local parity 검사 포함. 테스트 파일 이름 충돌을 해결한 뒤 새 프로세스에서 전체 선택 범위를 다시 실행. 전체 저장소 CI suite 실행이나 운영 Jira 부하 실측을 의미하지 않음.

기존 provenance 테스트 2건은 HEAD 파일만 OS 임시 경로에 읽어 실행해도 동일 실패함을 확인. 무효화된 캐시의 삭제를 기대하던 assertion을 기존 보존 정책에 맞춰 수정: fresh 조회 불가, invalidated 유지, 원래 수집 시각 보존. 제품의 캐시 보존 동작은 변경하지 않음.

## 한계

단일 Jira 응답은 provider가 받은 후 JSON으로 파싱됨. 한 티켓에 비정상적으로 거대한 본문이 있는 경우, 행 수·파싱 후 바이트 검사만으로 최초 응답의 메모리를 완전히 제한할 수 없음. 내부 canonical 티켓 캐시 여러 건을 복원하는 일부 경로도 집계 검사보다 역직렬화가 먼저임. Windows Job 상한과 외부 복구 관리자가 마지막 보호층. 작업 프로세스가 복구되면 창도 다시 열릴 수 있음. OS 종료·강제 종료까지 막는 보장은 하지 않음.

`--reload` 개발 실행은 기존 reload 관리자를 사용하므로 운영 Windows Job 상한·복구 트레이 적용 대상이 아님. 개발 환경에서는 요청·본문·수집·메모리 압박 제어가 적용됨. POSIX는 소프트 보호와 프로세스 그룹 정리만 지원.

테스트 산출물은 OS 임시 디렉터리에 격리하고 프로세스 종료 시 정리. 운영 배포는 별도 수행.
