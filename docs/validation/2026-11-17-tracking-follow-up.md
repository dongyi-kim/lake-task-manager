# Tracking 후속 수정 검증

## 범위

댓글 HTML 표시·접기, 조회 도구 모음·트리 조작, 완료 범주와 링크 활동 필터,
VOC 소속·제목 분류, 사용자 이름 장기 캐시, Task/Sub-task 가로 타임라인.

타임라인은 선택 기간의 자체 티켓 상태·댓글과 직속 하위 주요 변화를 별도 행으로 표시.
날짜 간격 보존, 동일 날짜의 여러 전환·댓글, 상태 변화 없음·부분 수집 구분.
실제 Vue 화면에서 사건 선택·키보드 이동·추가 조회 0 검증.

## 독립 리뷰와 처리

1. `app/jira/identity_service.py` — 새 이름 저장소만 서버별로 구분하면 조회 가능한 함수가 이전 `user:env:id` 캐시로 되돌아갈 수 있음. 이름 조회 캐시 키도 서버·환경으로 구분하고 회귀 검증 추가. 출처 없는 과거 이름 캐시는 자동 이관하지 않음.
2. `app/tracking/names.py` — 오래된 댓글·이력의 이름에 새 티켓 조회 시각을 붙이면 최신 이름을 덮어쓸 수 있음. 알려진 원본 수집 시각의 하한 사용, 출처 시각 미확인 작성자는 장기 캐시를 갱신하지 않음. 원본·저장 snapshot 보존.
3. `app/tracking/manager.py` — 조회 옵션을 열 때마다 과거 실행과 이름을 다시 읽는 비용. 누락된 이름만 초기 보완, 같은 대상의 반복 검사 방지, 묶음 저장. 관련 검증에서 옵션 3회 호출 시 과거 실행 조회·쓰기 각각 1회.
4. 변경 크기 — 약 1,600줄의 통합 diff를 한 단위로 검토하기 어려움. VOC, 댓글, 활동 필터, 화면 조작, 이름 캐시, 타임라인으로 커밋 분리. 새 모듈은 이름 저장·Tracking 이름 추출·타임라인 계산·표시로 분리.

breaking changes·context·change size·testing 관점 리뷰 수행. 테스트 리뷰에서 추가 결함 없음.

## 운영 자료의 한계

- 댓글 오류는 원문 HTML·인코딩·일반 텍스트 fixture로 재현. 운영 원문을 직접 확보한 검증은 아님.
- VOC 120개와 하위 120개를 중복 계층에 배치한 검증에서 240개 티켓·사건 유지.
- 로컬 mock의 적은 VOC 수는 조회 기간·모듈 소속으로 설명됨. 운영의 동일 증상을 확정하지 않음.
- Closed·Resolved는 모두 Done 범주면 같은 완료. 상단은 기간 중 완료 전환 업무 수이며 현재 완료 상태 수와 별도.
- 이름 캐시는 90일 신선도·365일 표시 보존. `/myself`와 티켓 캐시 수명은 유지.
- 실제 Jira·LLM 호출 없이 검증. 전체 저장소 suite는 기존 CI 정책에 따름.

## 계층 타임라인·샘플 확장

- 부모 Story `DL-5008` 요약에서는 시간축이 없고 근거 패널에만 있었음. Epic·부모 Task 선택 시 제목 아래 즉시 표시하도록 연결.
- 새 상세로 바꿀 때 이전 스크롤 위치가 남아 시간축을 가리던 증상 재현. 티켓 key / 구조 범위 id 변경 시 초기화, 같은 티켓 갱신 위치 보존.
- Epic→Task, Task→Sub-task 직속 주요 변화 구분. 공유 경로 중복 제거, 제목·번호·원본 근거 이동 유지. 날짜별 2건 미리보기와 펼치기.
- 완료 수는 `statusCategory=done`. 조회된 하위 작업을 분모로 사용하며, 미확인 상태·부분 수집에서는 비율을 확정하지 않음. 과거 시점 진척률이나 WBS SP 진척률 아님.
- 독립 리뷰: 부모 원문이 빠진 실제 Epic tree node에서도 시간축과 Epic 유형 유지. 상태·coverage는 합성하지 않음.
- 독립 리뷰: 원래 epicKey가 남아 있는 VOC를 선택 Epic 타임라인에 다시 섞지 않음. 표시 트리의 선택 범위와 분모·사건 일치.
- 일반 mock/local 월드에 Task 30·Sub-task 60·VOC 120건 추가. 기존 ETL Epic 4개·인력 설정 재사용, 기존 fixture·운영 자료 보존.
- 장기 대기 후 최근 착수, 동일 날짜 재오픈·재완료, 현재 활동 없음, 신규 접수, 담당 변경, 긴 댓글·표·코드 포함. 최대 댓글 75개·이력 65개. 일반 bridge는 전체 결과를 반환하므로 대량 payload 검증이며 강제 페이지 분할 실험은 아님.
