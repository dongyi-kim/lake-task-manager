## 0. 30초 요약

LTM(FastAPI+Vue3 무빌드 SPA) 안에 in-process 로 얹힌 LangGraph 멀티에이전트
"업무 착수 어시스턴트". 9역할(planner/historian/pmo/curator/refiner/assigner/reviewer/
operator/responder) StateGraph, 모든 쓰기는 HITL 승인 토큰(내용 지문 봉인),
mock(JIRA_ENV=mock, jira820 인메모리)에서 개발, 검증은 fake LLM 기본 + gpt-4o-mini 실측.

**핵심 설계 원칙 (전 코드에 반복됨)**
1. **판단은 모델, 보장은 코드** — 반복문·검증·취합은 코드가 하고(사전취합/가드),
   모델은 읽고 판단만. 프롬프트로 지시하고 코드로 한 번 더 막는다.
2. **재료가 이미 손안에 있으면 순회하지 않는다** — 도구 호출 한 번이 곧 LLM 왕복
   한 번이다. 부를 대상이 늘 같으면 코드가 미리 조회한다(§5-b).
3. **위임("알아서")이 질문을 이긴다** — 되묻기 금지·기본값 채움을 코드가 강제.
4. **HITL 지문**: 승인 화면에 보인 것과 실행되는 것이 sha256 지문으로 같아야 한다
   (`approval.py`). 카드 편집은 State draft 를 고치고 payload 를 재생성(`session._apply_overrides`).
5. **grounding**: 없는 키·틀린 제목·없는 사람은 코드가 잡는다(답변+티켓 본문 둘 다).

**지금 어디까지 왔나 (2026-08-09 기준)**: 지속 시나리오 루프 A~U(실측 결함 ~59건 수정)
→ 성능 최적화(163s→53s, 토큰 −72%) → **역할 정합 감사**(§5-c) → **품질 라운드 C**(생성,
§5-e) → **품질 라운드 D**(조사·답변, §5-f) 완료. **1020 tests green**,
**생성 스위트 20/20 한 실행 전수 통과**(기준선 16/20), 시나리오 배터리 **한 프로세스 한 실행 29/29**(평균 3.78).
다음 할 일은 §7 — **A 두 건은 여전히 사용자 확인 대기**, B 는 바로 진행 가능.

> **이 저장소에서 "품질을 올렸다"는 통과율로 말하지 않는다.** 배터리가 초록인데 답이

## 3. 코드 지도 (agent 부분)

```
app/agent/
├─ config.py        # provider 4-way(get_llm/get_embeddings), stream_usage, 429 재시도, llm_ready()
├─ approval.py      # HITL 토큰·지문(stage/approve/consume/amend_payload)
├─ compose.py       # 에디터 AI(단일 호출) + _badgeify(평문→뱃지 마크업)
├─ usage.py         # Meter — 역할·도구별 시간/토큰/캐시/비용, tiktoken 입력 가드
├─ routes.py        # /api/agent/* (chat/stream SSE·approve·cancel·compose·status)
├─ tools/           # @tool 26+종. _ident.py(식별자), search/survey/write/pmo/rag/file…
├─ retrieval/       # 정적 FAISS(knowledge/) + 동적 증분 인덱스(harvest/chunk/manifest)
├─ prompts/         # common.md(공통 페르소나), roles/*.md(역할 지시), base.py(persona 조립 — 캐시 정렬)
└─ workflow/
   ├─ state.py      # AgentState·Intent·Node·request_text()(원 요청 고정)·trace 리듀서
   ├─ graph.py      # StateGraph 조립 + 라우터(해석확인 분기·빠른 경로·fan-out)
   ├─ session.py    # ask/stream/resume(카드 편집 반영)/snapshot·이벤트 humanize(_events)
   ├─ grounding.py  # 날조 키·제목·사람 검출(답변+초안 본문)
   └─ agents/       # base(StructuredAgent/ToolAgent/TextAgent)·9역할. refiner.py 가 가장 두껍다(가드 무리)
knowledge/          # 정적 RAG 원천 — 04(구조 판단)·07(본문 가이드+최소 요건 슬롯)·08(렌더링)
tools/agent_*.py    # 위 하네스들
app/static/…/AgentView.js  # 챗 UI(플랜 체크리스트·뱃지 augment·카드 편집·대화 전환)
```

**refiner.py 의 가드 순서가 곧 로직이다** — 순서 민감. 두 갈래로 갈라져 있다:

`apply()` (초안 갈래, 494줄): 지정담당 강제(_apply_named_assignees) → 껍데기→Sub-Task
변환(+보정 분할) → subtask 모드 children 제거+지정 재적용 → 참고 병합(_merge_refs) →
날조 불릿 제거 → 주제 가드(_topic_drift→Reviewer 우회 금지) → Epic 실재·모듈 불일치 →
번호·단계 접기(_base_title) → 균등 배분 → 자식 담당 채움(부모 담당 폴백) → 구조-산출
어긋남 보정 → 하향 편향 보정(위임이면 _split_into_children) → 우선순위 정규화 →
PMO_VIT 제거 → **`_change_plan()` 호출** → 초안 병합("하나 더 추가해줘").

`_change_plan()` (변경 갈래, 285줄): 생성 요청에 변경 계획 금지 → 빈 값 제거 →
**필드 범위 제한**(말한 것만) → 우선순위 정규화 → **상대 날짜 코드 계산** + 방향 검증
("미뤄"인데 앞당기면 확인 요청) → before 값 조회 → 전이 해석(상태명→id) → 링크 조립 →
일괄(JQL 대상+필드) 조립 → 사번 실재 확인 → 초안 수정을 티켓 변경으로 오인한 것 폐기.

> 나눈 이유: 초안을 다듬는 일과 기존 티켓을 고치는 일은 재료도 실패 방식도 다른데
> 한 함수(773줄)에 있어 어느 가드가 어느 갈래의 것인지 읽어서는 알 수 없었다.

## 4. 대화 흐름 (2026-08-09 현재)

```
사용자 요청
 └ Planner(의도·sufficient·request_text 고정)
    ├ 막연한 plan_work·첫 턴·비위임 → Refiner(해석 확인: interpretation + 질문 2~3
    │    — 범위/모듈/Epic 배치. 슬롯 룰 _slot_audit: ASK/INFER/LATER) → 사용자 답
    ├ my_day/progress/activity → PMO(사전취합: 그룹활동·티켓진척) → Responder
    ├ ask+식별자 → Historian(topic_dossier 직결) → Curator → Responder
    └ 충분/위임/후속 → Historian(조사) → Refiner(초안) → Assigner∥Reviewer
         → 승인 카드(카드에서 ✎ 직접 수정 가능) → Operator(승인 후 생성) → Responder
```
SSE 이벤트: `start → plan(체크리스트) → step(도구 humanize)·node(단계 완료) →
token(Responder 스트리밍) → final`. UI 는 플랜 단위 [✓]/[▸]/[ ] + 세부 중첩 폴딩.

## 5-b. 성능 설계 원칙 (2026-08-09 최적화 라운드에서 확립)

> **재료가 이미 손안에 있으면 순회하지 않는다.**

도구 호출 한 번은 곧 **LLM 왕복 한 번**이다. 그런데 역할이 가진 도구가 코드 사전취합과
중복이면 모델은 그것을 매 턴 다시 부른다 — 생성 턴 하나에 refiner 만 12회·226k 토큰을
먹은 것이 그래서였다. 판단이 아닌 조회는 코드가 하고, 모델에게는 **결과만** 준다.

## 5-c. 역할 정합 감사 (2026-08-09, `98dda02`) — 왜 필요했나

성능 라운드에서 Refiner·Assigner 를 `ToolAgent` → `StructuredAgent` 로 바꾸며 도구를
전부 걷어냈다. **그런데 md 는 그대로 남아** "먼저 `search_rules` 를 불러라",
"`get_module_people` 로 후보를 모아라" 하고 **열 군데서** 시키고 있었다. 코드는 멀쩡히
돌고 849 테스트도 전부 통과했다 — 모델만 없는 도구를 찾아 헤맸다.

> **교훈: 역할의 형태를 바꾸면 그 역할의 프롬프트도 같이 바뀌어야 한다.**
> 코드와 프롬프트는 한 몸인데 테스트는 코드만 본다. 그래서 테스트를 하나 늘렸다
> (`test_agent_prompt_integrity.py` — 고치기 전 md 로 되돌려 실제로 4건 잡는 것 확인).

같은 감사에서 나온 나머지:

| 종류 | 무엇 |
|---|---|
| 역할 간 모순 | refiner.md 는 "prose 로 쓴 Sub-Task 후보는 결함", reviewer.md 는 "절대 문제 삼지 마라" |
| **경계 위반** | Assigner 가 "x1450 은 진행중 15건이라 부적합"이라 써 놓고 **자식 2건이 그 사람에게** 갔다. `draft_text` 에 자식이 안 보여 Assigner 가 배분할 수 없었다 → 자식 담당을 Assigner 로 이관 |
| 사전취합 회귀 | my_day 직결이 '미배정'이라는 **다른 기준**을 가로챘다(ReAct 에만 있던 `find_unassigned_tickets` 가 도달 불능) |
| 답변 결함 | "미뤄줘"인데 8-27→8-14 로 당긴 것을 아무도 안 짚음 · 같은 문장 두 번 |
| 카드 불일치 | `(구조: …)` 근거 줄을 **두 곳에서** 붙여, 재작성 왕복이 있으면 헤더(새 이유)와 근거 줄(옛 이유)이 달랐다 → 맨 끝에서 한 번만, 옛 줄은 지우고 다시 쓴다 |
| 코드 | `refiner.apply` 773→494줄(`_change_plan` 분리) · 줄바꿈이 공백으로 뭉개진 줄 5건 복구 |

> **사전취합의 함정(반복 주의)**: 사전취합이 자라 ReAct 를 건너뛰게 되면, **ReAct 에만
> 있던 도구는 조용히 도달 불능**이 된다. 재료에 넣을 것은 "모델이 부를 법한 것"이 아니라
> **질문이 요구하는 것**이다. 직결(L3a) 을 늘릴 때마다 이 갈래를 점검할 것.

### 이번 라운드의 진짜 소득 — 결함이 **한 부류**였다

여섯 건이 전부 같은 모양이었다. **코드가 만든 재료가 그것을 쓸 역할에 닿지 않는다.**
만드는 쪽도 쓰는 쪽도 각자 멀쩡해서 테스트가 초록이고, 모델이 "모르겠다"고 답하는 것으로만
드러난다. 그래서 통과율이 아니라 **답을 읽어야** 보인다.

| 끊긴 구간 | 증상 | 케이스 |
|---|---|---|
| `web_context` → Refiner | 웹 근거를 모아 놓고 초안에 안 씀 | 라운드 C |

> **★ 마지막 것이 앞의 셋의 바닥이었다.** `request_text` 는 손으로 고른 `pre_survey`
> 슬라이스 **두 개**로만 살아남고 있었고, 그 둘도 "요약이 재료를 흘린다"는 같은 이유로
> 그때그때 덧댄 것이었다. 개별 재료를 하나씩 잇는 것은 대증요법이다 — **역할 사이를 지나는
> 것이 무엇인지**가 한 자리에 없으면 이 부류는 계속 난다.

### 가드가 만든 회피로 (4건) — 막으면 다른 길로 샌다

인용 형식을 코드로 강제했더니 모델이 규칙을 **피하는 쪽**으로 움직였다.

| 회피 | 무엇을 했나 |
|---|---|
| 인용을 지운다 | 형식을 못 맞추겠으니 근거를 빼 버림 |
| 아무 URL 이나 빌려 온다 | 옆 티켓 링크를 갖다 붙임 |
| URL 자리에 지시문을 복사 | "materials 의 URL" 이라는 **문장**을 링크로 |
| 후보를 지운다 | 명단이 걸리니 명단째 삭제 |

> **★ 넷 중 둘이 "지워서 통과"였다.** 그래서 `name_as_id` 위반은 "지우라"가 아니라
> **맞는 id 를 집어 준다**. 가드의 출력이 "틀렸다"이면 모델은 가장 싼 순응인 삭제를 고른다 —
> 가드는 **고칠 방법을 함께** 줘야 답이 얇아지지 않는다. 답이 얇아지는 것을 코드로도 받쳤다
> (`_kept_substance` — 재작성이 길이 절반 미만이거나 티켓 키 절반을 잃으면 되돌린다).

### judge 는 양방향으로 틀렸다 — 게이트에서 뺐다

- 질문과 **다른 것**에 답한 출력에 6축 **5.0**
- 전부 맞은 답에 `answers_original=False` + 사실관계가 틀린 `worst`

그래서 통과 판정은 `intent`+`체커`(계약)만 보고, judge 점수는 **`⚑읽어볼 것` 표시**로만 쓴다.
정성 판정은 사용자 지시대로 **클로드가 직접** 출력을 읽어서 한다. 계약(`EXPECT`: story ·
must · must_not)이 29케이스 전부에 붙어 있어서, "무엇이 나와야 하는가"는 judge 가 아니라
**케이스에 미리 적혀 있다**.

### 모듈 별칭 — 코드가 뜻을 넘겨짚지 않으면서 두 모듈 걸침을 잡는 법

라운드 C 에서 미뤄 둔 STR2(§5-e 원인 **B**)를 여기서 닫았다. 문제는 이랬다: 자식(Sub-Task)은
**부모 컴포넌트로 집계된다.** 모듈이 다른 일을 자식으로 넣으면 Runtime 일이 Catalog 로
계상되는데, 티켓은 멀쩡해 보이고 어디서도 안 터진다.

코드가 "쿼리 엔진 = Runtime"을 알아야 잡을 수 있는데, 코드가 뜻을 추측하면 **그 추측이 곧
같은 결함**(남의 모듈에 계상)이다. 그래서 뜻의 매핑을 사람 손으로 옮겼다:

- `config/module-aliases.yaml` — 모듈 → 별칭. 출처는 `knowledge/03` 의 모듈 표
- `settings.resolve_module` 이 표기 정규화 → 별칭 순으로 보고, **둘 다 없으면 ""**
- `settings.modules_in_text` — 본문에 이름이 그대로 나온 모듈들(등장 순서)
- Refiner: 모듈이 **하나로 딱 떨어지는** 자식만 형제 Task 로 올린다. 컴포넌트가 빈 항목은
  제 본문이 부른 모듈로 채운다(비면 담당 찾기가 전사 명단으로 넓어진다)

> **★ 별칭은 좁게 적는다.** 이 표는 "티켓을 나눌지"를 바꾸므로, "운영"·"엔진"·"배포" 같은
> 흔한 낱말을 넣으면 아무 요청이나 두 모듈에 걸친 것이 된다. 못 찾는 쪽으로 틀리게 두고,
> 사용자가 형태를 입으로 말했으면(`said_shape`) 아예 건드리지 않는다.

> **초안이 덮은 모듈**을 맞대 보고, 빠진 쪽을 보정 호출 1회로 채운다(`_task_for_module`).

### 이 라운드에서 **내가 만든 결함 4건** — 가드가 가드를 깨는 방식

고친 것보다 이쪽이 다음 세션에 쓸모 있다. 넷 다 "가드를 넣었더니 옆이 깨졌다"인데
**깨지는 방식이 서로 달랐다.**

| 내가 넣은 것 | 무엇을 깨뜨렸나 |
|---|---|
| 모듈 승격(자식→형제 Task) | 자리를 옮기니 **본문 계약**이 바뀌었다 — Sub-Task 본문엔 배경이 없어도 되는데 Task 는 아니다 |
| `_can_parent_subtask` | 바로 아래 `elif subs` 가 그 항목들을 **전부 걷어내 초안 0건**이 됐다 |
| `_sharpen_dod` | 보정 안에서 예외가 나면 **초안이 통째로** 사라진다(항목이 dict 가 아닐 수 있다) |
| 승격 가드의 구조 갱신 | 승격이 없는 초안의 모양까지 덮어썼다(루프 밖 조건 하나로 걸어서) |

> 그래서 가드를 넣을 때 "무엇을 막는가"만큼 **"막은 뒤에 무엇이 남는가"** 를 본다 —
> 걷어내는 대신 **옮길 데가 있으면 옮긴다**(Epic 부모 → Epic Link + Task).
> 테스트에도 `assert got` 를 **맨 앞에** 둔다.

**내가 만든 결함도 같은 실행에서 나왔다** — 모듈이 다른 자식을 형제 Task 로 올렸더니
STR2 가 "작업 범위에 제외가 없다" 2건으로 떨어졌다. Sub-Task 본문은 배경을 쓰지 않는 것이
규칙이라(knowledge/07) 짧은데, 최상위로 올라오면 배경·범위(포함/제외)·완료 조건을 갖춰야
한다. **자리를 옮기면 그 자리의 규율도 따라가야 한다** — §5-e 의 "소유권을 옮기면 보장도
옮겨라"와 같은 말이고, 이번엔 본문 계약이었다(`_task_grade_body`).

그리고 "Epic 골라줘" 가드를 넣자마자 **§5-f 앞머리의 배선 결함이 그대로 재현됐다**:
`out["mode"]` 만 고치니 항목은 Task 인데 승인 카드의 모드는 `epic` 이었다(`draft` 는 이미
조립됐고 `items` 만 참조로 공유한다). 여섯 번 고친 부류가 일곱 번째로 나온 것이다.

### ★ 배터리가 자기 실행 중에 색인을 키운다 — "29/29" 를 의심하게 만든 것

**"한 번의 실행으로 전수 통과"를 증명하려다 배터리 자체의 결함을 찾았다.**

29케이스를 **한 프로세스로** 돌리면 26/29 가 나오는데, 두 번 돌린 실패 집합이 서로 달랐다
(MOD8·DATA5·PROG1 / REC9·PROG1·DATA11). 그 케이스들을 2~3건짜리 작은 배치로 돌리면
**전부 통과**한다. 케이스가 흔들린 게 아니라 **상태가 실행 내내 자란 것**이다.

범인은 **동적 색인**(`CACHE_DIR/agent_index/dynamic`)이다. 에이전트가 본 것을 누적하는데,
제품에서는 그게 기능이고 배터리에서는 오염이다 — 앞 케이스가 훑은 티켓·문서가 뒤 케이스의
의미 검색에 섞여 든다. 그래서 **케이스 순서와 그날까지의 누적량이 결과를 바꾼다.**

`tools/agent_scenarios.py` 가 **실행 시작에 `dynamic_index.reset()`** 하도록 했다(케이스마다는
아니다 — 멀티턴 케이스는 자기 턴 사이의 누적이 필요하다). 26/29 → 27/29 → **케이스마다
비우도록 바꾼 뒤 28/29**. 남은 하나(DATA4)는 오염이 아니라 **실결함**이었고, 그것을
고쳐 **29/29** 가 됐다 — 오염을 걷어내니 진짜 결함이 드러난 것이다.

> **★ "14/14 + 15/15" 는 "29/29" 가 아니다.** 두 번의 실행을 더한 것이고, 한 실행으로
> 29를 돌리면 다른 결과가 나온다. 배터리를 나눠 돌린 값을 합쳐 적으면 **이 오염이 통계에서
> 사라진다.** 앞으로 전수 통과를 주장할 때는 **한 프로세스 한 실행**의 값만 쓸 것.

## 8. 작업 규율 (이 저장소에서 지켜온 것)

- 커밋은 원자적으로, 메시지에 실측 근거(어떤 사고를 왜 이렇게 고쳤나)를 남긴다.
- 프롬프트를 고치면 반드시 코드 가드도 검토("프롬프트로 막았는데 재발" 패턴이 많았다).
- **역할의 형태를 바꾸면 그 역할의 md 도 같이 바꾼다** — 도구를 걷어냈는데 md 가 남아
  열 군데서 유령 도구를 시킨 사고가 있었다(§5-c). 이제 테스트가 지킨다.
- **소유권을 옮기면 그 소유권에 걸린 보장도 옮긴다** — 자식 담당의 주인을 Assigner 로
  이관하면서 "분량 분할은 골고루" 가드가 Refiner 에 남아 덮어쓰기 뒤편이 됐다(§5-e).
  경계를 옮길 때 "이 값에 걸린 코드 보장이 어디 있나"를 같이 찾을 것.
- **★ 지시는 코드가 실행 가능하게 만들어 줘야 한다** — "판단은 모델, 보장은 코드"의 다음
  층위다. 한 세션에 같은 부류가 **네 번** 나왔고 전부 "프롬프트는 시키는데 재료·경로가
  그걸 못 받쳐 주는" 것이었다:
  ① "도메인 관계를 전개하라" ↔ `web_context` 가 Refiner 에 안 갔다
  ② "변경 이력이 없으면 최초 구축 티켓의 값이 현재 값" ↔ **그 티켓이 어느 것인지** 안 짚어 줬다
  ③ "재료의 URL 을 복사하라" ↔ 두 라운드 고쳐도 안 옮겨서 결국 **코드가 붙였다**
  ④ "이력을 처음부터 끝까지 훑어라" ↔ 연표와 변경이력이 **두 블록**이라 하나만 옮겼다
  → 규칙을 프롬프트에 적기 전에 묻는다: **그 규칙이 가리키는 것을 재료가 짚어 주는가?**
  재료가 두 갈래면 모델은 하나만 고르고, 대상을 안 짚어 주면 규칙은 문장으로만 남는다.
  프롬프트를 세 번 고치는 것보다 배선을 한 번 고치는 것이 싸고 확실하다.

  형식을 **검사에서 빼지 마라** — 딱 그 형식으로 샌다(`1.` 번호 참조가 검사 밖이었다).

- **★ 케이스가 틀렸을 수도 있다** — BULK3 는 Epic 밑에 Sub-Task 를 달라고 하는 케이스였다.
  도메인 규칙상 불가능한 요구라 **에이전트가 맞고 케이스가 틀렸다.** 실패를 보면 먼저
  "이 케이스가 요구하는 것이 규칙상 가능한가"를 확인할 것 — 아니면 코드를 규칙 위반
  방향으로 고치게 된다. 가장 비싼 종류의 오수정이다.
  **다만 케이스를 고치고 끝내지 마라** — 같은 날 STR1 이 바로 그 규칙(Epic 밑 Sub-Task)을
  **어긴 초안**을 냈는데, 강등 가드가 부모의 실재만 봐서 통과시켰다. 규칙을 확인했으면
  **그것을 지키는 코드가 있는지** 그 자리에서 같이 볼 것.
- **가드는 제 일 아닌 것을 건드리면 안 된다** — 모듈 승격 가드의 구조 갱신을 처음에 루프
  밖 조건 하나로 걸었더니, **승격이 없는 초안의 모양까지** 덮어썼다. "언제 발동하는가"만큼
  "발동하지 않을 때 아무것도 안 하는가"를 같이 볼 것.
- **★ 나쁜 산출물보다 나쁜 것은 산출물 없음이다** — 잘못된 부모를 막았더니 아래 분기가
  그 항목을 **전부 걷어내 초안이 0건**이 됐다(실측 STR1). 답변은 "수정이 필요합니다"라고
  말하는데 승인할 것이 없으니 사용자에겐 먹통이다. **걷어내기 전에 옮길 데를 먼저 찾고**,
  테스트에는 `assert 항목이 있다` 를 **맨 앞에** 둔다.
- **보정 호출 안에서 예외가 나면 본 흐름이 죽는다** — 모델 산출은 무엇이든 올 수 있으니
  (dict 가 아닌 항목도 온다) 보정은 통째로 감싸고, 실패하면 **원본을 그대로 둔다**.
- **테스트에서 `tools/` 배터리 모듈을 import 하지 마라** — import 시점에 LLM 모델
  환경변수를 덮어써서 무관한 테스트가 죽는다(실측: `test_settings_put_*`). 소스를
  읽어서 검사할 것.
- 변경 후 실제 앱을 띄워 확인한다. 테스트 통과만으로 완료 보고하지 않는다.
- **파이프가 종료 코드를 삼킨다** — `pytest … | tail -1 && git commit` 으로 깨진 파일을
  커밋한 적이 있다(e12df65). 테스트 결과는 따로 확인하고 커밋한다.
